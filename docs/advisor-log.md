Security / fake-counting / fraud controls (founder asked for special steps)
D43 (LOCKED-DEFAULT) — Payout controls (solo founder, manual payouts).

* Fixed monthly payout run + minimum payout.
* First payout only after identity verification + onboarding call.
* Account-title (name) must match the verified identity before the first payout and after any payout-detail change.
* Payout-detail change → 7-day hold, notification to the old email, MFA required.
* Release requires step-up MFA + typed confirmation, plus a 24–48h cooling-off after approval with an out-of-band alert (email/Telegram) so a compromised admin session cannot move money silently.
* Per-run payout cap. Payout log with reference + proof, immutable.

D44 (LOCKED-DEFAULT) — Hold period. Bonus accrues immediately but becomes releasable only 90 days after the underlying payment (beyond the usual chargeback window, typically up to ~120 days). Refund/chargeback creates a clawback entry; if already paid out, it becomes a negative-balance bucket recovered from future accruals.
D45 (LOCKED-DEFAULT) — Economic invariant and control total.

* Reward value never exceeds the cleared net revenue produced by the qualifying referrals.
* Every commission/credit row references the Paddle transaction ID.
* Daily reconciliation: total commissions ≤ 8.88% × Paddle-verified net revenue (pull from the Paddle API); mismatch → alert, never auto-correct.
* Ledger is append-only; amounts stored as integer minor units; deterministic rounding; app DB role can INSERT but not UPDATE/DELETE ledger rows.

D46 (LOCKED-DEFAULT) — "Real use" definition for a qualifying referral (interprets the founder's "complete month use"): referred account is new; logged in on ≥2 distinct days; has created a store with ≥3 products or published it; paid amount ≥ discount floor; Paddle customer ≠ referrer; no refund in 14 days; no chargeback. Anti-ring flags (manual review, no auto-reward): burst of ≥N referrals per hour, ghost accounts (paid, never used), shared normalised email or Paddle address, referred and referrer related. No device/IP fingerprinting (founder rule) — payment-side and behaviour-side signals only.
D47 (LOCKED-DEFAULT) — Attribution integrity. First-valid-link-wins stored server-side at signup from a signed referral token (HMAC, timestamp, partner ID, 60-day expiry). Only top-level navigations count (reject iframe/hidden requests via `Sec-Fetch-*` headers). Click rate limits per source. Partner terms ban cookie stuffing, forced redirects, hidden iframes, incentivised or misleading traffic. Alerts on abnormal click→signup ratios.
D48 (LOCKED-DEFAULT) — Payment-state integrity. Entitlements and referral state change only from signature-verified Paddle webhooks (HMAC, timestamp tolerance, raw body, event-ID idempotency) — never from a client redirect or "success" page. Checkout uses server-created Paddle transactions with server-side price IDs; the client cannot change plan, price or cycle. Same for seller gateways: verify webhook signatures and compare amount/currency to the order total on the server.
D49 (LOCKED-DEFAULT) — Business-logic and race controls. Reward claim, Launch Assurance, Founding Members cap (100) and rung evaluation use DB-level atomicity (unique constraints, `SELECT … FOR UPDATE` or conditional UPDATE) with idempotency keys. All windows computed in UTC on the server. Decimal/integer money maths only. Discount floor enforced server-side where Paddle discounts are created. Concurrency tests for double-claim, 101st Founding Member, parallel rung evaluation.
D50 (LOCKED-DEFAULT) — Counters and analytics integrity. No client-supplied counts. Events ingested server-side with bot filtering, de-duplication, rate limits and signed event IDs. Visitor counts used for Launch Assurance are unique, bot-filtered and capped. Public counters (sellers/stores/partners) are computed server-side from verified data. Admin dashboards flag impossible jumps.
D51 (LOCKED-DEFAULT) — Signup/abuse hardening. Invisible bot challenge (Cloudflare Turnstile — no popup; founder did not object, advisor decision) on signup, login, password reset and partner application; disposable-email blocklist; email normalisation; per-IP/subnet velocity limits; free-tier quotas (storage, stores, emails); outbound email caps to protect sender reputation; alerts on signup spikes.
